# KDBX conformance fixtures

Two committed artifacts that every KDBX implementation in this repository is
checked against. They exist because ADR 0052 §4.5 freezes one mapping shared by
a Rust crate and a TypeScript adapter, and because the `keepass` crate's KDBX4
**writer** is experimental — a Rust-only round-trip could pass while producing
files no real KeePass client opens.

| File | What it is |
|------|------------|
| `roundtrip.kdbx` | A small KeePass database exercising every mapped field type |
| `roundtrip.expected.json` | The sealed-store item set that database maps to |

## `roundtrip.kdbx`

| | |
|---|---|
| Format | KDBX **4.1** |
| Password | `correct horse battery staple` |
| Keyfile | none |
| Outer cipher | AES-256 |
| Inner cipher | ChaCha20 |
| Compression | GZip |
| KDF | Argon2id — 16 MiB, 2 passes, 4 lanes |

> **Why 4.1 and not 4.0.** ADR 0052 §4.5 asks for KDBX 4.0. `keepass 0.13.22`'s
> writer rejects every version other than `KDB4(1)`, so the fixture — and every
> export this repository produces — is 4.1. KeePass 2.x, KeePassXC and
> `kdbxweb` all read 4.1.

> **Why the reduced Argon2 work factors.** The fixture is opened by several test
> suites on every run, including one running Argon2 in WebAssembly. 16 MiB / 2
> passes keeps that cheap. It is a test artifact, not a recommendation: real
> exports default to 64 MiB / 2 passes (`Argon2Params::default`).

Nothing in the file is a real credential. The passwords are literal
`fixture-*` strings and the TOTP seed is the RFC 6238 Appendix B test vector
(`GEZDGNBVGY3TQOJQGEZDGNBVGY3TQOJQ`, ASCII `12345678901234567890`).

### What it covers

| Entry | Group | Exercises |
|-------|-------|-----------|
| `Example Mail` | `Personal/Email` | `Title`, `UserName`, `Password`, `URL`, multi-line `Notes`, a custom string field, TOTP as an `otpauth://` URI in the `otp` attribute |
| `Example Mail` (again) | `Personal/Email` | duplicate title in one group → the ` (2)` collision suffix |
| `Deploy Token` | `Shared/Ops` | KeePassXC `TimeOtp-*` attributes synthesized into one `otpauth://` URI; a field that exports `Protected="True"` |
| `Tab\there` | `Weird/Name` | group- and title-name sanitization (`/` and a tab both → `_`) |
| `Root Note` | root | a root-level entry with no password — line one stays empty |

Two levels of nesting on two different branches, so group-path mapping is
exercised rather than assumed.

## `roundtrip.expected.json`

The **sealed-store** mapping of `roundtrip.kdbx`: store path → the entry that
lands in the store. Stable, sorted by path, pretty-printed with a trailing
newline.

```json
{
  "format": "opensesame-kdbx-conformance/1",
  "items": {
    "<store path>": {
      "secret": "<line one>",
      "trailer": ["<trailer line>", "..."],
      "otp": "otpauth://..." | null
    }
  }
}
```

- `trailer` excludes blank lines and the `otpauth://` line — the latter is
  reported once, under `otp`.
- Continuation lines (multi-line values) appear verbatim, two-space prefix and
  all.

The normative statement of how these values are derived is
[`crates/kdbx-bridge/README.md`](../../crates/kdbx-bridge/README.md).

## Who reads these

- **Rust** — `crates/kdbx-bridge/tests/conformance.rs` asserts that mapping the
  committed `.kdbx` reproduces the committed `.json` byte for byte, that the
  file really is the constrained writer profile, and that it needs the
  documented password.
- **TypeScript** — the pages KDBX adapter's vitest opens the *same* `.kdbx`
  with `kdbxweb` + `hash-wasm` and asserts it derives the same mapped items.
  Two independent implementations agreeing on one committed file is the
  cross-implementation guard; a Rust-only round-trip would not be.

## Regenerating

Owned by `crates/kdbx-bridge` (task T-KDBX-CORE). Regenerate **both** files
together — the KDBX bytes change every run (fresh seeds, IVs and UUIDs), so a
stale `.json` is a failing test, not a silent drift:

```bash
cargo +1.88.0 test -p opensesame-kdbx-bridge --test conformance -- \
  --ignored regenerate_fixture
```

Changing the fixture is changing a contract two implementations build against.
Expect the TypeScript suite to need re-running, and say so in the commit.

If a consumer needs an expectation in *its own* item shape — the pages vault
model, say, rather than the sealed store's — that belongs in a separate,
consumer-owned file generated from this same `.kdbx` (`roundtrip.pages.json`
and the like). Do not repurpose `roundtrip.expected.json`: it is the
sealed-store mapping, and `conformance.rs` regenerates it.
