# One-shot prompt: passkey portability, custody, regeneration, and AI-assisted rotation

> Copy everything below the line into a coding agent that can spawn parallel
> subagents (isolated worktrees recommended). It is self-contained: no other
> conversation or document is required.

---

## Mission

You are the orchestrator. Implement OpenSesame's **passkey portability**
(custody, import/export, regeneration) and **AI-assisted credential rotation**
in one run by delegating the work packages below to **parallel** subagents.
The packages are deliberately independent — **no ordering, no phases, no
timelines**: each package owns a disjoint set of files, carries its full spec
including verbatim type contracts, and self-verifies. Spawn **all of them at
once**, merge their results, run the acceptance checks, and stop.

The product problem: a passkey's private key is generated inside an
authenticator built never to release it. That is what makes passkeys
phishing-resistant, and it is also what locks users into whichever password
manager generated them. OpenSesame's answer is three concrete capabilities —
**carry** the passkeys that can move (FIDO CXF and native manager exports),
**become the authenticator** for new ones (E2EE vault custody + a browser
WebAuthn provider), and **regenerate** the ones that cannot move (guided
re-enrollment at the relying party, then retirement of the old credential).
Alongside it, the credential-hygiene engine that already detects weak, reused,
and stale credentials gets connected to the rotation machinery that already
exists but has no caller.

**ADR 0052 (`docs/adr/0052-passkey-portability-custody-and-regeneration.md`)
is already committed and is binding.** Read it first. Everything below
implements it. Where this prompt and ADR 0052 disagree, ADR 0052 wins and you
should report the discrepancy.

## Adversarial critique (binding — read before designing anything)

The naive version of this feature is wrong in specific, expensive ways. These
corrections are ground truth for every subagent.

### 1. "Brokering" another manager's passkeys is impossible, not merely hard

Do not build, name, or imply a feature that proxies WebAuthn ceremonies for a
credential held by 1Password, iCloud Keychain, or Bitwarden. Satisfying a
ceremony requires the private key; the holder will not release it. Any UI
string suggesting OpenSesame can "use your existing passkeys" without import
or re-enrollment is a **bug against ADR 0052 §2**. Foreign passkeys are
recorded as `custody: "external"` — tracked state, never a proxy.

### 2. CXF import is narrower in practice than it sounds

Do not represent CXF support as "import your passkeys from anywhere."
Reality: the exchange format is still stabilizing; several managers expose
export only through OS-mediated flows rather than a file you can hand us; and
some CXF payloads are HPKE-encrypted rather than plain JSON. **Scope: parse
plaintext CXF JSON plus the native formats that already carry key material
(Bitwarden JSON `fido2Credentials`, 1Password 1PUX, Proton Pass JSON).**
Encrypted-envelope CXF and the online CXP protocol are explicitly out of
scope; detect them and emit a clear skip reason rather than a parse failure.

### 3. Vault-custodied passkeys are a real security downgrade in one dimension — say so

Today an XSS in the Pages origin leaks passwords. After this work it also
leaks passkey private keys, and the vault body is decrypted as a whole when
unlocked, so there is no per-item scoping to hide behind. This trade is
accepted (a synced software authenticator is what every passkey manager is),
but it must be **stated in the ADR consequences and in user-facing copy**, and
it raises the bar on: no new third-party scripts in Pages, no widening of CSP,
no logging path that can serialize an item. Do not silently pretend custody is
free.

### 4. The `navigator.credentials` proxy must fail open, always

A provider that throws breaks login on real sites. Rules: capture the native
implementation at `document_start` before wrapping; wrap in try/catch and
**fall through to native on any error, timeout, or user cancel**; never
proxy a request for an rpId we have no credential for and no create intent
on; never fake `isUserVerifyingPlatformAuthenticatorAvailable` or
`isConditionalMediationAvailable`. Ship a kill switch that fully unhooks. A
page that captured `navigator.credentials` before us wins, and that is
correct behavior — do not fight it.

### 5. The relying-party identifier comes from the browser, never the page

The content script's `sender.origin` is the only authority on which rpId a
ceremony may target. A page claiming `rpId: "google.com"` from
`evil.example` must be rejected using the host-suffix rules already written in
`apps/pages/src/lib/vault/unlock-methods.ts`. This is the single highest-value
security assertion in the whole work package; it needs a dedicated test.

### 6. A bundled list of passkey-capable sites is the wrong primary mechanism

The plan's original "ship a static `passkey-rps.json`" is a maintenance
treadmill and goes stale immediately. **Better primary signal: the extension
already proxies `navigator.credentials`, so it observes which sites actually
invoke WebAuthn during normal browsing.** Record that observation locally
(rpId + "this site offered WebAuthn", no timestamps of visits, no page
content, never synced off-device without consent) and use it to drive the
`passkey-eligible` finding. The static list ships only as a small seed for
users who have not installed the extension, and it must be presented as
incomplete rather than authoritative.

### 7. "Full auto" is mostly unavailable, and the toggle must not lie

Automatic end-to-end rotation requires a provider-side capability: MINT
(ADR 0049) or INVOKE-THROUGH (ADR 0048). Those exist for API/agent
credentials, **not for consumer web logins**, which is precisely where the
"Apple auto-updates weak passwords" comparison points. Do not build a UI that
offers `auto` for targets that structurally cannot honor it. The mode is a
statement about *consent*, not capability: capability sets the ceiling, and a
target without one terminates in `needs-human` regardless of mode. Label it
truthfully in the UI ("this site has no rotation API — OpenSesame will prepare
the change and you complete it").

### 8. Retirement of the old credential cannot be verified

OpenSesame cannot confirm a user deleted the old passkey at the relying party.
`reenrollState: "old-retired"` is **user-asserted**, and the model, the copy,
and any report must say so. Do not present it as verified.

### 9. Importing a passkey that still exists in the source manager creates a duplicate

Both authenticators hold the same credential ID and both can sign. This is
usually benign, but signature counters diverge. Emit `signCount: 0` (the
multi-device-credential convention; 0 means "not supported" per spec) so
relying parties do not run clone detection against us — the same class of bug
`docs/security/audit-2026-08-08-passkey-counter-device-fence.md` fixed
server-side. Surface duplicate-credential state in the UI so the user knows
two copies exist.

### 10. Zero AAGUID with `fmt: "none"` will be rejected by some relying parties

Enterprise RPs that require attestation will refuse a self-attested software
authenticator. This is a known, permanent limitation, not a bug to chase.
Detect the failure and tell the user their organization requires a hardware
key rather than retrying.

### 11. The rotation FSM and the broker disagree about what a rotation is

`crates/rotation` models eleven states with rollback; `connection-broker`
records three (`Requested`/`Succeeded`/`Failed`). Wiring them is not a rename:
the broker's persisted state becomes the FSM state name, and every legal
transition must be enforced by the FSM rather than by the caller. The existing
Kani/shuttle/fuzz proofs cover the pure crate and must keep passing; add
integration tests proving the broker cannot perform a transition the FSM
forbids.

### 12. In-memory registries are the actual reliability bug

`RotationRegistry` and the gateway's `OnceLock` registry lose every policy and
job on restart, so a scheduler built on them would silently forget work. The
durable tables are not a nice-to-have; without them the feature is theater.
Model them on `migrations/0008_backup_outbox.sql`, which already solves
claim/lease/backoff/dead-letter for the backup actor.

### 13. Both secret scrubbers are shallow, and passkey items are nested

`RotationJob::public_view()` (Rust) and `assertNoSecrets()` (TypeScript) both
remove **top-level keys only**. A `privateKeyPkcs8B64` nested inside a `target`,
a `metadata` blob, or an item object sails straight through. The existing
surfaces got away with it because their payloads are flat. Do not assume that
protection extends to anything you add: keep new event payloads flat, and where
you cannot, deepen the scrub. `packages/observability`'s `redactDeep` +
`SENSITIVE_KEY_PATTERN` is the deep-walk implementation to follow.

Related trap: `SENSITIVE_KEY_PATTERN` is anchored (`^…$`) and already contains
`private[_-]?key` — which does **not** match `privateKeyPkcs8B64`. Adding the
field name to the pattern is a real edit, not a no-op, and both
`LOG_REDACT_PATHS` (bare **and** `*.`-prefixed) and `SENSITIVE_KEY_PATTERN` must
be extended.

### 14. CXF export is the first plaintext export this codebase has ever had

Today the only bytes that leave the vault are ciphertext: `exportSealed()`
emits a sealed envelope, and the offline backup path refuses anything else.
Adding a plaintext CXF exporter is a deliberate change to that posture, not a
feature increment. It is justified — portability has to be symmetric or ADR
0052 §3 is hypocrisy — but it must be gated behind an explicit user
confirmation, flagged in the return value when the payload carries private
keys, and never reachable from an automated path.

### 15. Health findings live on the wrong side of the E2EE boundary from rotation jobs

Vault health is computed client-side over decrypted items the server cannot
read. Rotation jobs are server-side over connections and sealed-store paths.
**There is no automatic bridge and you must not invent one that ships vault
contents to the gateway.** The only sanctioned link is an explicit,
user-initiated export of a redacted task list (rpIds + issue codes, no
usernames, no secrets).

### House conventions every TypeScript package must obey

These are enforced by `pnpm lint:anti-slop` (vendored Oxlint plugin, all rules
at `error`) and by `tsconfig.base.json`. Violating them is a build failure, not
a style nit.

- **Never `x as unknown as T`.** Use `overlapCast` from `@opensesame/os-domain`.
  Any remaining type assertion needs a `// SAFETY:` comment.
- **Never `unknown` on a parameter or return.** Use `BoundaryValue`, or a
  generic (`function f<Thrown>(error: Thrown)` — the house workaround, visible
  in `describeWebauthnError`).
- **Never `Record<string, unknown>`.** Use `JsonObject` / `BoundaryObject`.
- **Never `vi.mock`.** The codebase's universal test hook is the **seam
  pattern**: a module exports a mutable `xSeams` object holding default
  implementations, the public function delegates through it, and tests swap
  entries with `Object.assign`, restoring in `afterEach`. Existing examples:
  `passwordSeams`, `settingsSeams`, `vaultHooksSeams`, `unlockMethodsSeams`,
  `offlineBackupSeams`, `reactDomSeams`. If your new module needs injection,
  add a seam — do not reach for a mocking library.
- **Never bare `typeof x === "string"`** outside a type guard. Use `isString`,
  `isNumber`, `isBoolean`, `isJsonObject`, `isTypeofObject`.
- **Relative imports carry explicit `.js` extensions**, even in `.ts` sources
  (NodeNext). `verbatimModuleSyntax` is on, so type-only imports must say
  `import type`.
- **`exactOptionalPropertyTypes: true`** and **`noUncheckedIndexedAccess: true`**.
  An optional field must be *omitted*, not set to `undefined`; indexed access
  yields `T | undefined` and must be narrowed.
- **Tests are colocated** (`src/**/*.test.ts`), declare their environment with a
  per-file `/** @vitest-environment jsdom */` docblock, and import named
  helpers from `"vitest"` (no globals). `apps/pages` deliberately has **no**
  `vitest.config.ts` — it inherits `vite.config.ts`.
- **New packages under `packages/` need no workspace or turbo edit** —
  `pnpm-workspace.yaml` globs `packages/*`, and `turbo.json` defines only six
  generic tasks (`build`, `dev`, `typecheck`, `test`, `test:integration`,
  `test:e2e`). Match those script names and you are wired in. A new *app* would
  need an explicit `pnpm-workspace.yaml` entry; this work adds none.
- **New package shape**: `private: true`, `type: "module"`, exact pinned
  versions, and `exports` pointing directly at `./src/index.ts` for both
  `types` and `default` (there is no build step, no `dist`). Copy
  `packages/policy` verbatim as the template.
- **Workspace dependencies are always `workspace:*`** — never a range, never
  `link:`.
- **`packages/contracts` uses Zod v3** (`3.25.67`, a real dependency of that
  package): every contract is a `<Thing>Schema` const followed by
  `export type <Thing> = z.infer<typeof <Thing>Schema>`, and objects are
  `.strict()` so an unexpected secret-shaped field fails parsing loudly instead
  of being silently stripped.
- **`@simplewebauthn/server@13.2.2` is already a root devDependency** — use it
  for verification tests without adding a new dep.
- **`pnpm test` is `turbo run test`; `pre-push` runs `pnpm typecheck && pnpm test`
  by default.** A package with a broken `test` or `typecheck` script blocks
  every push in the repo, not just yours.

### C1 — Vault item model additions

*Owner: **WP-MODEL** (`apps/pages/src/lib/vault/model.ts`).*

`PasskeyItem` keeps every existing field and gains these. **All new fields are
optional**, so a vault sealed before this work deserializes unchanged:

```ts
export type PasskeyCustody = "vault" | "external";
export type PasskeyProvenance = "imported" | "generated" | "recorded";
export type ReenrollState = "none" | "new-enrolled" | "old-retired";

export type PasskeyItem = BaseItem & {
  kind: "passkey";
  rpId: string;
  username: string;
  credentialIdB64: string;
  publicKeyB64: string;
  /** Where the private key actually lives. */
  authenticator: "platform" | "cross-platform";
  /** True when this credential can unlock the vault via the WebAuthn PRF extension. */
  unlocksVault: boolean;

  // --- custody (new) ---
  /**
   * PKCS#8 private key, base64. Present only when custody === "vault".
   * Treated exactly like CertificateItem.privateKeyPem: never logged, never
   * rendered, never leaves the sealed body.
   */
  privateKeyPkcs8B64?: string;
  /** COSE_Key public key, base64. CXF carries COSE; keep alongside publicKeyB64. */
  cosePublicKeyB64?: string;
  /** Always 0 for vault-custodied credentials. See adversarial critique §9. */
  signCount?: number;
  userHandleB64?: string;
  discoverable?: boolean;
  /** COSE algorithm identifier: -7 = ES256, -8 = EdDSA. ES256 is required. */
  alg?: number;
  transports?: string[];
  /** Absent means "external" — legacy items are metadata-only records. */
  custody?: PasskeyCustody;
  provenance?: PasskeyProvenance;
  /** Product name the credential was imported from, for honest UI copy. */
  importedFrom?: string;
  /** Another credential at the same RP holds the same credentialId elsewhere. */
  duplicateOfExternal?: boolean;

  // --- regeneration (new) ---
  supersededById?: string;
  /** ISO timestamp. USER-ASSERTED — OpenSesame cannot verify RP-side deletion. */
  retiredAt?: string | null;
  reenrollState?: ReenrollState;
};
```

`LoginItem` gains the same three regeneration fields (`supersededById`,
`retiredAt`, `reenrollState`) with identical semantics, and nothing else.

Helper predicates WP-MODEL must export (every other package uses these instead
of testing `custody` inline):

```ts
/** True when OpenSesame holds the private key and can sign for this credential. */
export function isVaultCustodied(item: PasskeyItem): boolean;
/** True when the credential is a record of a key held by another authenticator. */

/** True when the item has been superseded and the user marked the old one retired. */
```

### C3 — Key-format helpers

*Owner: **WP-MODEL** (`apps/pages/src/lib/vault/passkey-keys.ts`).*

Pure functions over WebCrypto, no DOM, no React. Every other package imports
these rather than writing its own COSE handling.

```ts
/** base64url ⇄ bytes, tolerant of padded and unpadded input. */
export function b64uToBytes(value: string): Uint8Array;
export function bytesToB64u(bytes: Uint8Array): string;
/** Standard base64 (the encoding vault items store). */
export function b64ToBytes(value: string): Uint8Array;
export function bytesToB64(bytes: Uint8Array): string;

/** COSE_Key (EC2/P-256, alg -7) → raw SPKI bytes and back. */
export function coseToSpki(cose: Uint8Array): Uint8Array;
export function spkiToCose(spki: Uint8Array): Uint8Array;

/** Accepts PKCS#8, SEC1, or JWK; returns PKCS#8 base64. Throws on anything else. */
export function toPkcs8B64(input: Uint8Array | JsonWebKey, alg: number): Promise<string>;

/** Import a stored PKCS#8 key for signing. Non-extractable where possible. */
export function importSigningKey(pkcs8B64: string, alg: number): Promise<CryptoKey>;
/** Derive the COSE public key from a private key, for items missing one. */
export function publicCoseFromPrivate(key: CryptoKey): Promise<Uint8Array>;

/** ECDSA raw (r||s) → DER, which is what WebAuthn assertions carry. */
export function rawSignatureToDer(raw: Uint8Array): Uint8Array;
```

Supported algorithm set for this work: **ES256 (-7) is required**; Ed25519
(-8) is feature-detected and may be declined with a typed error. Anything else

### C5 — Rotation mode

*Owner: **WP-SETTINGS** for the client half, **WP-ROTATION-STORE** for the
server half. The literal union is identical on both sides.*

```ts
export type RotationMode = "auto" | "assisted";
```

Semantics (ADR 0052 §7), binding on both planes:

- `auto` — capability-backed rotations run end to end; deterministic
  client-side steps auto-advance.
- `assisted` — every ceremony halts at a consent step before anything changes
  at the relying party.
- **Capability sets the ceiling regardless of mode.** A target with neither
  MINT nor INVOKE-THROUGH terminates in `needs-human` even under `auto`. The
  UI must never offer `auto` as though it will complete such a target.

Rust mirror, owned by **WP-ROTATION-STORE**:

```rust

#[serde(rename_all = "snake_case")]

```

### C7 — Extension ⇄ Pages ceremony protocol

*Owner: **WP-EXT-BRIDGE** defines it; **WP-EXT-PROVIDER** and
**WP-PAGES-SIGNER** both implement against it.*

**The architecture is forced, not chosen.** Two facts settle it: an MV3 service
worker has no `navigator.credentials` at all, and a `chrome-extension://`
origin cannot run a WebAuthn ceremony for an arbitrary relying party's rpId.
The extension therefore **cannot** be the authenticator; it observes, decides,
and relays. Signing happens in the Pages origin, which already owns vault
unlock. Do not spend time re-litigating this.

Note that OpenSesame's own authenticator (WP-AUTHENTICATOR) is a **software**
authenticator built on `crypto.subtle` — it does not call
`navigator.credentials` and so is not subject to that restriction. What the
restriction rules out is the extension calling the *browser's* WebAuthn API on
a page's behalf.

Message shapes, versioned from day one:

```ts
export type CeremonyRequest = {
  v: 1;
  /** Single-use, generated by the extension background with crypto.randomUUID(). */
  nonce: string;
  kind: "create" | "get";
  /** AUTHORITATIVE — derived from sender.origin, never from the page. */
  rpId: string;
  /** The page's origin, for clientDataJSON. */
  origin: string;
  /** base64url challenge from the page's PublicKeyCredentialRequest/CreationOptions. */
  challengeB64u: string;
  /** create only */
  user?: { idB64u: string; name: string; displayName: string };
  /** create only: algorithms the RP will accept, COSE identifiers. */
  pubKeyCredParams?: number[];
  /** get only: credential IDs the RP will accept; empty means discoverable. */
  allowCredentialIdsB64u?: string[];
  userVerification: "required" | "preferred" | "discouraged";
};

export type CeremonyResponse =
  | { v: 1; nonce: string; ok: true; kind: "create" | "get"; credential: unknown }
  | { v: 1; nonce: string; ok: false; reason: CeremonyDeclineReason };

export type CeremonyDeclineReason =
  | "no-credential"        // nothing in the vault for this rpId
  | "user-cancelled"
  | "vault-locked"
  | "unsupported-algorithm"
  | "rp-id-rejected"       // host-suffix validation failed
  | "timeout"
  | "internal-error";
```

**Every decline reason means the same thing to the provider: fall through to
the native implementation.** There is no reason value that permits failing the
page's ceremony outright.

`credential` on success is the standard WebAuthn JSON response
(`PublicKeyCredentialWithAttestationJSON` / `…WithAssertionJSON`) as produced
by the marshalling in `apps/mobile-mfa/src/webauthn.ts`.

### C8 — Observed relying-party capability record

*Owner: **WP-EXT-PROVIDER** (extension-local storage), consumed by

### Three landmines specific to this package

1. **`tests/pact.test.mjs` is a source-order oracle.** It reads

   those sequences, and **write a matching source-order oracle for your own

   Vitest. A new test file will silently never run. Widen the script (e.g.

3. **An MV3 service worker has no `navigator.credentials`,** and a

5. **Off by default.** A stored setting gates the whole provider; when off, the

6. **Permissions** — `wxt.config.ts` gains the `https://*/*` content-script

7. **RP observation (contract C8)** — when a page invokes WebAuthn, record the

8. Preserve the existing `opensesame.health` and `opensesame.sync_cursor`

## WP-ROTATION-STORE — durable rotation queue and the gateway actor

**OWNS:**

- `migrations/0011_rotation_durable.sql` (new — `0011` is the next free number)
- `crates/storage/src/lib.rs` — the `MIGRATIONS` table entry and the row
  structs/accessors your actor needs
- `apps/gateway/src/rotation_actor.rs` (new)
- `apps/gateway/src/routes/rotation.rs`
- `apps/gateway/src/routes/mod.rs` — **only** the new `.route(...)` line and
  `mod` declaration
- `apps/gateway/src/routes/contract.rs` — **only** to add new route
  expectations; do not alter existing frozen entries
- `apps/gateway/src/main.rs` — **only** the `mod` + `tokio::spawn` line

**Do not own:** `crates/connection-broker/**`, `crates/rotation/**`, worker,
MCP.

### Two-edit rules you will otherwise miss

- **A migration needs two edits.** The `.sql` file alone does nothing:
  `crates/storage/src/lib.rs` holds a `const MIGRATIONS: &[(&str, &str)]` of
  `include_str!`'d files applied in order, and your migration must be appended
  there as `("0011_rotation_durable", include_str!("../../../migrations/0011_rotation_durable.sql"))`.
  Migrations are append-only; never rewrite an applied version. Copy the
  existing test convention that applies `&MIGRATIONS[..N]` and then asserts the
  new migration applies cleanly to an already-migrated database (see
  `backup_outbox_migration_applies_to_an_already_migrated_database`).
- **A route needs three edits.** The handler, a `.route(...)` line in
  `apps/gateway/src/routes/mod.rs` (axum 0.8 syntax is `{id}`, not `:id`, and
  the path must be a **string literal** because `contract.rs` parses `mod.rs`
  as text), and either an OpenAPI `paths:` entry in
  `api/openapi/openapi.yaml` or a tuple in `UNDOCUMENTED_ROUTES` in
  `contract.rs`. Two contract tests enforce both directions: an undocumented
  route fails, and a stale allowlist entry also fails. A third test builds the
  real router and asserts every documented route answers something other than
  404/405.

### Spec

1. **Schema**, modeled directly on `migrations/0008_backup_outbox.sql`:
   - `rotation_policies` — persisted policies (id, target kind + reference,
     project/org, interval, `mode` per **C5**, enabled, timestamps).
   - `rotation_jobs` — id, policy id, target, `state` (**C6** string),
     `attempts`, `available_at`, `last_error`, lease columns
     (claimed-by / claimed-until), created/updated, plus a **partial index on
     unclaimed, due rows** exactly as the outbox migration does.
2. **Actor** — copy the `apps/gateway/src/backup.rs` saga shape exactly:
   `pub async fn run(state: AppState)` with a `tokio::select!` on a `Notify`
   plus an interval tick, and a separate `pub async fn pass(...)` that is
   **public for tests with its externally-facing base injected** so it can run
   against a mock. Reuse the constants (`BATCH_LIMIT = 256`,
   `CLAIM_LEASE_SECONDS = 120`, `MAX_ATTEMPTS = 8`), the
   `enum StepError { Suspend(String), Retry(String) }` classification with
   `compensate_suspend` / `compensate_retry`, the exponential backoff
   `(5i64 << attempts.min(9)).min(3600)`, and an env-var tick interval with a
   5s default. Never let an error escape `run` — log and continue, as backup
   does.
3. **The scheduler that was missing:** each tick, evaluate persisted policies
   with `policy_due_at(&policy, last_run, now)` from
   `crates/connection-broker` and enqueue due jobs. This function currently has
   **zero callers**; you are its first. Enqueue must be idempotent — a due
   policy must not spawn duplicate jobs across ticks or across concurrent
   gateway instances (a lease plus a uniqueness constraint carries this).
   Note `policy_due_at` returns false for a disabled policy or an unparseable
   interval, and true when `last_run` is `None`.
4. **Durability before the bus.** Persist the job, *then* publish the event.
   `crates/connection-broker` enforces this on itself with a source-order test
   (`request_inserts_before_publish`, which reads its own file as text and
   compares indices). Write the equivalent oracle for your actor — it is the
   house pattern, and it is what stops a refactor from silently reordering a
   durability guarantee.
5. **Routes stay additive.** `POST /api/v1/rotations`, `GET /api/v1/rotations`,
   `GET /api/v1/rotations/{id}` keep their exact request/response shapes —
   including the injected `"secrets_returned": false` key and the `202`/`200`/
   `409` status choices — but are now backed by the durable store instead of
   the process-global `OnceLock` registry. Preserve the tenant-non-leaking
   behavior where a job belonging to another organization and a missing job
   both return the identical `404 {"error":"not_found"}`. Add one new route
   for assisted-mode approval (`POST /api/v1/rotations/{id}/approve`) moving a
   job out of `pending_approval`. **Ownership-fence it exactly as the existing
   mutation routes are** (`resolve_caller`, the
   `x-opensesame-organization` operator-header rules, sessions forbidden from
   selecting an organization) — an unfenced approval route would let any caller
   authorize a credential change.
6. Never return credential bytes from any route. Responses keep using
   `RotationJob::public_view()`, whose scrub is **top-level only** — so keep
   response payloads flat (adversarial critique §13).
7. Emit the existing CloudEvents plus a per-transition event; do not rename
   `credential.rotation.requested|succeeded|failed`, because
   `apps/worker/src/rotation.ts` matches on them.
8. Note `apps/gateway/src/backup_bus.rs`'s existing comment that the memory
   backend must skip its consumer or it would steal rotation events — make sure
   your wiring does not reintroduce that conflict.

## WP-ROTATION-FSM — wire the proof-verified state machine into the broker

**OWNS:**

- `crates/connection-broker/src/rotation.rs`
- `crates/connection-broker/Cargo.toml`
- `crates/rotation/**`

**Do not own:** gateway, migrations, worker, MCP.

### Spec

1. Add `opensesame-rotation` (path `../rotation`) as a dependency of
   `crates/connection-broker` and make `execute_connection_rotation` advance
   the FSM rather than flipping a three-value status. **The FSM decides
   transition legality** via `RotationState::can_transition` /
   `transition(to) -> Result<Self, RotationError>`; the caller may never
   construct a next state directly (adversarial critique §11). New Rust
   dependencies go in the root `[workspace.dependencies]` and are referenced as
   `{ workspace = true }`; path deps to sibling crates are written directly.
   The legal edges are a single exhaustive `matches!` allowlist in
   `crates/rotation/src/lib.rs` — read it before assuming an edge exists. Note
   that `RollbackStarted` is reachable only from `CandidateInstalled`,
   `CandidateVerified`, `CandidateActivated`, `DependentsUpdated`, and
   `Observing`, and `ReconciliationRequired` only from `CandidateInstalled`,
   `CandidateActivated`, and `PreviousRevoked`. If you need an edge that does
   not exist, extend the FSM **and** its proofs — do not work around it.
2. Map rollback states to compensating actions, mirroring how
   `apps/gateway/src/backup.rs` compensates. `ReconciliationRequired` is a real
   outcome, not an error to swallow.
3. **Capability-ordered execution (ADR 0048 D4):**
   - MINT-capable connection → fully automatic via the ADR 0049 derived
     materialization path;
   - INVOKE-THROUGH-capable → rotate through `crates/invoke-through`, whose
     fences (https-only, exact-host allowlist, **no redirect following**, no
     cookie store) must not be relaxed — do not add a dependency or a redirect
     follow to make a provider work;
   - neither → terminal `needs_human`.
4. **Mode enforcement:** in `assisted` (**C5**), a job halts at
   `pending_approval` before the activate transition even when capability
   would allow completion. In `auto` it proceeds. Mode never manufactures a
   capability.
5. Sealed-store targets keep using `crates/sealed-store/src/update.rs` and
   `generate.rs` and stay **agent-hostile**: the crate proposes a new value;
   the human CLI seals it. Do not add a path where an agent seals a store entry.
6. Keep `RotationJob::public_view()`'s stripping behavior; extend the forbidden
   key set if you add fields.
7. The existing Kani proofs (`completed_is_a_sink`,
   `cannot_revoke_before_observe`), the shuttle test, and the fuzz target must
   keep passing. If you extend the FSM, extend the proofs.
