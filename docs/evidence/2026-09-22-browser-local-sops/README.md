# Browser-local SOPS — evidence

SOPS YAML and JSON encrypt, decrypt, edit, import and export with local age
identities, running entirely in the static browser application: no Host, no
daemon, no extension, no installed `sops`, no environment variable, no Node
service, no serverless function, no separately installed runtime.

Decision: [ADR 0130](../../adr/0130-browser-local-sops.md), which supersedes
[ADR 0129](../../adr/0129-vault-key-protection-manifest.md) §7.
Reference: [`docs/security/sops-wire-compatibility.md`](../../security/sops-wire-compatibility.md).

## What was wrong

ADR 0129 §7 said SOPS "run[s] in the static browser" and that a native
`sops` binary "is not required for the PWA". Two commits stood between that
and this one.

As of `7724fa3`, `lib/vault/protection/sops-browser.ts` said SOPS YAML/JSON
was "not available in-browser" and pointed the person at
`opensesame pass protect sops-encrypt|sops-decrypt` "with
`OPENSESAME_SOPS_BIN`" — an instruction nobody on GitHub Pages can follow,
phrased so an absent feature read as a configuration mistake.

`424bc48`, this branch's parent, removed that wording and started a browser
engine: about 2,100 lines, a vault-secrets sheet, and no way to open an
arbitrary SOPS document — while the Formats panel's SOPS row already claimed
read, write and "this browser". Nothing checked any of it against upstream
`sops` in either direction.

So the state being replaced is a panel whose claim about itself was ahead of
what it could do. This change makes the claim true: the whole workflow is
reachable from Settings → Formats, and it is verified against the pinned
upstream binary in both wire directions and both edit directions.
`pnpm verify:sops-browser` scans the built bundle so no native runtime —
`OPENSESAME_SOPS_BIN` included — can come back by accident.

## Reproduce

```bash
# product gate (mandatory): unit suites, two production builds, real
# browser at subpath and domain root, online and offline, bundle scan
PLAYWRIGHT_CHROMIUM=/opt/pw-browsers/chromium pnpm verify:sops-browser

# compatibility gate (mandatory): the pinned, checksum-verified upstream
# binary, both wire directions and both edit directions.
# A missing oracle exits 2 as INCOMPLETE — never a pass.
pnpm verify:sops-conformance

# optional, opt-in, separately reported
pnpm verify:sops-cloud-live

# merge the three into results.json + traceability.md
node scripts/test/sops-evidence.mjs
```

Measurements (not a gate, nothing thresholds on them):

```bash
SOPS_MEASURE=1 pnpm --filter @opensesame/pages exec vitest run \
  src/lib/sops/engine.measure.test.ts
```

## A note on what "blocked-external" means

Four cases need a disposable cloud KMS key that this environment does not
have and that this work will not provision. They are reported as
**blocked-external**, counted separately, and never rolled into the passed
total. The cloud adapters' wire encodings are unit-tested against upstream's
documented request and response shapes; that is a different and weaker kind
of evidence than a live call, and it is labelled as such.

## Test material

All identities under `apps/pages/src/lib/sops/fixtures/upstream/` are
**synthetic**, generated by `apps/pages/scripts/sops-fixtures.mjs`, marked
as non-secret in the file itself, and scoped to fixtures. They protect
nothing. No real vault was read, no production secret was used, and no
billable cloud resource was created.
