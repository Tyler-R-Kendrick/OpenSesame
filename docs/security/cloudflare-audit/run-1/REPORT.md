### HIGH: Shared-origin storage chooses the federation token endpoint and an unsigned ID token is saved

Fingerprint: `app-core.federation.storage-selected-token-endpoint`.

The checked-in Pages profile is shared_origin_demo on https://tyler-r-kendrick.github.io. Boundary 13 and storage-ownership.ts state that a path is not origin isolation, so another document on that origin can write the OpenSesame localStorage key. completeSignInDefault posts the authorization code, redirect URI, client id, and PKCE verifier to pending.tokenEndpoint and never substitutes the compiled issuer endpoint. readIdentity then decodes the returned JWT and checks iss, aud, and exp, but not the signature, on the assumption that the token came from the issuer token endpoint. decodeJwtEnvelope accepts an alg-none header only when every segment, including the signature, is non-empty base64url; an empty signature segment is rejected, and a non-empty unchecked segment is accepted. requireActiveUpstreamSession calls pending.sessionCheckEndpoint when that field is set, and any result other than HTTP 401 is success, including a missing endpoint. A same-origin writer can therefore rewrite a live pending record so an in-progress code and verifier are sent to an attacker server, and can plant a record that stores an unsigned token with iss https://shoo.dev when the attacker check does not return 401. saveSession writes that identity even when jwksUri is omitted, but loadSession then clears the row because identityFromJwt requires a string jwksUri. With jwksUri set, loadSession returns the forged subject. The compiled mock issuer http://127.0.0.1:9090 has no session check, so the same unsigned-token path saves a mock session after only the attacker token response. Sealing does not stop the write: a value that is not an at-rest seal is returned as plaintext, including after a sealed value is overwritten. Planting opensesame:federation:session directly also makes loadSession return an unsigned Shoo subject with no token POST; that write is the documented shared store. The additional crossing is the callback code, which is not in shared storage, being posted with the verifier to the storage-chosen token endpoint before the session check. The comparable static-auth Shoo passthrough pins https://shoo.dev/session/check and accepts only status active; app-core does not share that fail-closed pin. The ambient exchange has the same unbound tokenEndpoint and jwksUri shape, but ambient SSO returns null unless that capability is installed, and that path was not executed. An orgSlug record skips the issuer allowlist and does not save a federation session.

Lower-trust principal: A same-origin document writes the federation pending record so its issuer is a compiled trusted issuer and its token and session-check URLs are an attacker server. When OpenSesame completes the callback, it sends the code and PKCE verifier to that server and, if the server returns an unchecked token and the session check does not reject with HTTP 401, stores that token as the federation session when jwksUri is a string.

Source trace:

- entrypoint: `packages/app-core/src/lib/federation-pending.ts:37` `readRawPending` — Lower-trust entry. The PKCE record is read from origin localStorage key opensesame:federation:pkce, then sessionStorage. On the shared github.io origin that store is writable by every document of the account, not only this app path.
- propagation: `packages/app-core/src/lib/at-rest/web-storage.ts:88` `read` — localStore().getItem goes through sealedWebStorage. A value that is not an at-rest seal is returned as plaintext, so a same-origin writer does not need the at-rest key to plant the pending record. Overwriting a sealed value with plaintext is also returned as plaintext.
- propagation: `packages/app-core/src/lib/federation-pending.ts:45` `parsePending` — The JSON is overlap-cast with no check of tokenEndpoint, sessionCheckEndpoint, or jwksUri. A numeric createdAt older than ten minutes is stale. A missing createdAt is not aged out.
- propagation: `packages/app-core/src/lib/federation.ts:613` `completeSignInDefault` — The authorization code, redirect_uri, client_id, and code_verifier are POSTed to pending.tokenEndpoint as application/x-www-form-urlencoded with credentials omitted. The URL is not replaced with the compiled upstream token endpoint.
- propagation: `packages/app-core/src/lib/federation.ts:746` `readIdentity` — The ID token is decoded and checked for issuer, audience, expiry, and pairwise_sub or sub. The signature is not verified. Issuer https://shoo.dev and http://127.0.0.1:9090 are both in TRUSTED_UPSTREAMS, so an unchecked payload with one of those iss values passes when the envelope has three non-empty base64url segments.
- propagation: `packages/app-core/src/lib/federation.ts:506` `requireActiveUpstreamSession` — The session-check URL is pending.sessionCheckEndpoint or, if absent, the compiled URL. A missing URL, a transport error, or any HTTP status other than 401 returns success. The mock issuer has no compiled check.
- sink: `packages/app-core/src/lib/federation.ts:852` `saveSession` — When orgSlug is absent, saveSession writes the identity, including the attacker-supplied pairwise subject and the raw ID token, through writeFederationSessionJson. loadSession later accepts that stored token without a signature check when jwksUri is a string, and clears the row when it is not.

Conditions:

- system_configuration: The deployment uses the checked-in shared_origin_demo profile, or any other origin where a second document can script the same origin. mayPairLocalAuthority is false there. A dedicated origin would require script execution inside the app origin, which this profile does not require.
- authorization_role: The attacker is another page or script on that origin, such as a sibling GitHub Pages project or the account's user-site path. That page can read and write origin localStorage and can open the origin IndexedDB. A page on a different origin cannot.
- data_state: For code theft, beginSignIn has stored a live pending record and the attacker rewrites tokenEndpoint before the callback. For a durable forged session through this exchange, the planted record includes a string jwksUri; omitting it still sends the code, but loadSession then clears the saved row. createdAt must be a recent number or omitted; createdAt 0 is older than ten minutes and was refused.
- user_interaction: The person loads the OpenSesame document on that origin with the callback code and state. Code theft also needs a sign-in to be in progress. Session forgery needs that document to process the callback query the attacker can open.

Bounded reproduction:

- Bundle the real completeSignIn, readIdentity, requireActiveUpstreamSession, and sealed web-storage read with esbuild. Do not contact the network. Point fetch at a local stub that records the URL, method, and body and returns an unchecked ID token or an HTTP status.
- Install a host whose securityProfile is the checked-in shared_origin_demo object, whose page origin is https://tyler-r-kendrick.github.io and base path is /OpenSesame/, and whose local storage is an in-memory map. Defaults already leave remote Identity API and operator providers empty.
- Write the Shoo pending payload as plaintext under opensesame:federation:pkce, once without jwksUri and once with a string jwksUri, set the page search to ?code=attacker-code&state=state-1, and call completeSignIn, then loadSession.
- Repeat with the same attacker token endpoint and no sessionCheckEndpoint override so the compiled https://shoo.dev/session/check stub returns HTTP 401. Then repeat with the mock issuer payload and no session check. A Shoo payload with createdAt 0 is a negative check only. Also overwrite a sealed pending value with plaintext, and separately write opensesame:federation:session directly.
- Run that bundle through sandbox-run.sh with node --max-old-space-size=128. The sandbox allows PATH, HOME, TMPDIR, LANG, and LC_ALL, blocks external network, and sets a 1 GiB virtual-memory cap and a 25 second timeout. The script printed its results; process teardown in this sandbox then aborted on a node bundled-root-certificate assertion.

Observed result: shared_origin_demo resolved for https://tyler-r-kendrick.github.io and mayPairLocalAuthority was false. Plaintext under opensesame:federation:pkce was returned by the sealed reader, including after a sealed value was overwritten. The Shoo payload with no jwksUri POSTed to https://attacker.example/token with grant_type, code attacker-code, the redirect URI, client id, and verifier, then POSTed to https://attacker.example/check, and saveSession wrote issuer https://shoo.dev, pairwise subject forged-subject, and email forged@attacker.example. The following loadSession returned null and removed that row. The same payload with jwksUri https://shoo.dev/.well-known/jwks.json left loadSession returning forged-subject. With the compiled Shoo session check left in place, the token POST still went to https://attacker.example/token and HTTP 401 from https://shoo.dev/session/check raised login_required and left no saved session. The mock issuer saved pairwise subject mock-forged after only the attacker token POST, and loadSession returned it. The same Shoo payload with createdAt 0 was refused as an expired sign-in and saved nothing. An empty signature segment was rejected as invalid_token. A direct plaintext write of opensesame:federation:session, with no token POST, made loadSession return pairwise subject direct-plant. Redemption of the code at the real Shoo token endpoint was not attempted.

Impact: The app sends the authorization code and PKCE verifier to the attacker URL before the session check runs. That code is not in shared storage. The body is what a redemption at the real token endpoint requires; redemption itself was not observed. With a string jwksUri the app also keeps an attacker-chosen pairwise subject as the Shoo or mock federation session. A direct write of the session key can plant that local subject without the exchange, and the forged token does not decrypt an existing end-to-end vault. Likelihood: The shipped Pages profile is the shared github.io origin, so another document already on that origin can write the pending record. A page on a different origin cannot. Publishing or scripting that origin still requires a foothold on the account, and stealing a real code also needs a sign-in inside the pending window. Overall high does not exceed impact high.

Smallest source fix: At exchange time, ignore tokenEndpoint and sessionCheckEndpoint from storage when the issuer has compiled endpoints. Post the code only to that compiled token endpoint, or, for an operator issuer with no compiled endpoint, to a URL whose origin equals the issuer origin. Call only the compiled Shoo session-check URL and accept the sign-in only on an explicit active result. Where no compiled check exists, verify the ID token signature against the compiled JWKS or refuse that issuer outside tests. Do not treat the loopback mock issuer as a production session issuer without one of those checks. Apply the same origin pin in the ambient exchange before verifyBrowserIdTokenClaims; that path was not executed here.

### HIGH: Tenant join grants organization membership to the caller after verified-email auto-link binds the identity to another principal

Fingerprint: `control-plane.org-join.email-retarget-membership`.

POST /v1/organizations/tenants/:slug/join authenticates the caller with any live provisional bearer, verifies the organization id_token, and asks attachVerifiedExternalIdentity to bind the subject. When the token carries an email the organization is allowed to treat as verified and another principal already owns that verified email, the new identity row is stored on that other principal. The join handler then calls jitJoinOrganization with the caller's principal id. The caller receives the membership, including owner when an active SCIM row maps the subject to owner, while the identity remains on the email owner. The caller's session is left on the original provisional principal.

Lower-trust principal: A principal that already holds its own live provisional bearer presents an organization id_token whose verified email is already owned by a different principal.

### HIGH: SCIM deprovision does not revoke members who signed in through the organization LDAP directory

Fingerprint: `control-plane.scim.principalsForSubject.omits-directory-issuer`.

PATCH or DELETE that deactivates a SCIM user is supposed to drop that subject's membership and the provisional sessions that membership authorized. principalsForSubject searches kinds oidc, oauth2, saml, ldap, and email, but only under organization.ssoIssuer and organization.samlIssuer. LDAP sign-in stores the external identity as kind ldap with issuer ldapIssuer(config), the directory URL's scheme, host, and port, which is not either of those strings. The handler still returns 200 after deprovision and does not check that anyone was revoked. revokeOrganizationMembership, the only revocation on this path, is therefore not called, so the membership row and provisional sessions stay. The same call does revoke a principal whose oidc identity is stored under ssoIssuer. applyRole uses the same lookup, so a Groups role push misses these members too. When native SAML is configured with metadata and samlIssuer is empty, admission stores the metadata entityID, and that issuer is also absent from this list. Directory sync does not close the gap: it revokes an LDAP member only when a later scan no longer contains that subject.

Lower-trust principal: A member who bound through the organization LDAP directory keeps their membership and existing provisional bearer after the directory deactivates the matching SCIM user.

Source trace:

- entrypoint: `packages/control-plane/src/routes/scim.ts:441` `PATCH /:organizationId/scim/v2/Users/:id` — An authenticated provisioning token or active owner submits a PatchOp that sets active to false. authenticate has already bound the caller to this organization. DELETE of an active user is the same deprovision.
- propagation: `packages/control-plane/src/routes/scim.ts:487` `deprovision call` — After the SCIM row is saved inactive, deprovision is the only revocation. The handler then audits success and returns 200 whether or not any principal was found.
- propagation: `packages/control-plane/src/routes/scim-effects.ts:87` `principalsForSubject` — Issuers are only organization.ssoIssuer and organization.samlIssuer. kind ldap is queried, but with those issuers, not ldapIssuer of the org LDAP config.
- sink: `packages/control-plane/src/routes/scim-effects.ts:140` `deprovision` — revokeOrganizationMembership runs only for principals returned by that lookup. The LDAP principal is not among them, so the membership row and provisional sessions stay.

Conditions:

- authentication_level: The deactivation is performed by a live SCIM provisioning token for the organization, or by an active owner session, both of which authenticate accepts.
- data_state: The member has an external identity kind ldap, issuer ldapIssuer of this organization's LDAP config, and subject equal to the SCIM user's externalId or userName, plus an organization membership and a live provisional session.
- system_configuration: The organization has an LDAP directory configured. Its ssoIssuer and samlIssuer are not that directory URL. The same miss applies to a native SAML identity only when samlIssuer is empty and the stored issuer is the metadata entityID.

Bounded reproduction:

- Call the stripped ldapIssuer with url ldaps://dir.acme.example:636/dc=acme?x=1.

- Repeat with an oidc identity for subject ada at issuer https://idp.example mapped to prn_oidc, and with a saml identity offered only at issuer https://idp.example/metadata for subject bea.

Observed result: ldapIssuer returned ldaps://dir.acme.example:636. For carol, findByTuple ran ten times and every issuer was https://idp.example; the directory issuer was never queried and revoke was not called. ### HIGH: Shared startup denylist omits LD_AUDIT, so an env template loads an audit object in the credential-bearing child

Fingerprint: `packages/cli/startup-env-denylist-omits-ld-audit`.

credentialStartupEnvKeys is the only startup-hook denylist for both the TypeScript opensesame-id helper and the Rust opensesame password agent. It reserves LD_PRELOAD and LD_LIBRARY_PATH and does not reserve glibc LD_AUDIT. An environment template is lower-trust input: the operator chooses the command, and the template is supposed to be rejected when it names an interpreter or dynamic-linker hook. validateRunTemplate, assertSafeRunName, and the Rust validate_run_template and validate_run_assignments consult only that list, so a literal LD_AUDIT assignment is accepted and passed through as op run --env-file. helperEnvironment and scrub_startup remove only listed names. On the TypeScript path the provider child is a node wrapper whose script deletes OP_SERVICE_ACCOUNT_TOKEN only after the dynamic linker has started the process. On the Rust path Env::Run forwards the same unrejected bytes, authenticate() may then place the service token on the op command, and internal_exec removes that token only when it starts the selected command. A glibc parent that was itself started under LD_AUDIT is already running the library before either scrub; that inherited case is not a separate boundary. The boundary the denylist exists to enforce is introduction of the hook by the template. The same omitted key is not a second fingerprint. The name check also accepts an LD_AUDIT=op:// assignment, but the executed load used a literal path in the template.

Lower-trust principal: A process that can answer as the loopback Host the runner is already calling returns, after the page is open, a run view for a different id and for origin B while the page and vault context remain origin A, and A's arm expires during that pass.

Source trace:

- entrypoint: `apps/browser-extension/runner/host.ts:70` `hostConnection` — getRun forwards getAgentRun's decoded Host body for the opened run id into the runner and does not compare that body to the requested id or to the origin already being driven.
- propagation: `packages/api-client/src/agent-runs.ts:161` `getAgentRun` — The decoded view is returned whenever it is shaped like a run. Its id and origin are the body fields, not the id in the request path.
- propagation: `apps/browser-extension/runner/drive.ts:133` `driveRun` — skipReason is applied to that fresh view before every claim. The DriverDeps created at open still name the original run id, origin, tab, and vault context.
- propagation: `apps/browser-extension/runner/readiness.ts:22` `skipReason` — The arm, browser grant, and credential checks use current.origin from the Host body. They do not use the origin stored on the open page.
- sink: `apps/browser-extension/runner/driver.ts:72` `fill` — fill_credential resolves current_password for the opened context origin and pages.fill writes that value into the page that was opened for it.

Conditions:

- authentication_level: The extension already holds a Host session and has opened a drive for origin A from listRuns while A was armed, granted, and credentialed.
- authorization_role: Some other origin B remains armed, browser-granted, and present in the vault, and a recovery recipient and private-window permission are still set, so a view naming B passes skipReason.
- data_state: A's arm expires during driveRun, so isArmed(A) is false while lapse has not run again and A's host permission is still held. An options-page Stop revokes the grant immediately and is outside this window. After this pass returns, the next tick's lapse revokes the grant.
- system_configuration: The loopback Host the extension is calling returns a getRun body whose origin is not the opened run, with expires_at still ahead of the runner clock. The in-repo gateway serializes the stored target_origin for the path id and does not update that column.

Bounded reproduction:

- Arm https://rp.example for a short TTL and https://other.example for longer, grant both, store a distinct credential for each, pin a recovery recipient, and allow a private window.
- List one agent-driving run whose id is run:1 and whose origin is https://rp.example, with expires_at still ahead of the runner clock, and queue navigate to that origin, fill_credential of current_password, and submit.
- On the first getRun, return that same run. On later getRun calls, move only the settings clock past https://rp.example's expiresAt, leave its browser grant in place, and return the payload above.
- Repeat with getRun still returning id run:1 and origin https://rp.example after the same clock advance.

Observed result: With the swapped body, the runner opened run:1 on https://rp.example, claimed only run:1, and settled navigate, fill_credential, and submit. The fill port received https://rp.example's vault password and not https://other.example's, while isArmed(https://rp.example) was false, https://other.example stayed armed, and the grant for https://rp.example was still held. A second tick() during that pass was the same promise. With the origin left unchanged, the runner settled only navigate, skipped run:1 as not_armed, and did not fill or submit. In both cases a later tick then revoked the https://rp.example grant.

Impact: After the opened origin is no longer armed, the runner still writes that origin's current password into the page it already opened and can submit it, and this pass does not revoke the host permission. The password is not returned to the Host or taken from the other origin. The grant is revoked on the next tick once the pass returns, including when the step queue goes idle. Likelihood: The host base is loopback-pinned, and the in-repo gateway returns the stored target_origin for the path id without any update of that column. A drive also cannot start for an origin that fails skipReason on listRuns. The extension has to be talking to a Host that misreports a later getRun, some other origin must still pass skipReason, and the opened origin's arm must expire during that in-flight pass. A normal Stop click revokes the grant and is not this window. Overall low does not exceed impact medium.

Smallest source fix: Before skipReason, reject a fresh view whose id or origin differs from the run the page was opened for, and do not claim. The arm check then stays on that same origin, so expiry makes driveRun return and the next tick can lapse the grant. Also reject a getAgentRun body whose id is not the requested id. Add a regression that expires only the opened origin and swaps the getRun origin after the first step, expecting no further claim, and keep the case where an unchanged origin stops with not_armed.
