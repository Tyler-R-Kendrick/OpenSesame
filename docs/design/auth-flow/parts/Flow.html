One screen, two facts

A device knows who is signed in and which key opens a vault. They are separate ledgers with separate exits, and the unlock screen states both. Neither ever stands in for the other.

Who the account · Identity plane · ends with Sign out

Ways in — what setup allowed Google via shoo.dev (compiled in) · an operator's own IdP · org SSO / SAML / LDAP · magic link · your own issuer · guest, always.
→
Assertion A signed id_token for this origin — pairwise, no PII unless asked — vetted by the broker's /session/check and kept until exp.
→
Principal With an Identity API: provisional on arrival, linked on sign-in, one principal for many identities. Without one, the assertion is the whole account.
→
Named on screen Above both unlock tabs, and as the first segment of who@vault:/ inside. Provider, broker, and a short principal tail — never a raw subject.
Sign out Forgets the assertion, revokes the Identity session (bearer and cookie), locks the vault. Lands on the Sign in tab, which says so. shoo.dev itself keeps its Google session — shoo.dev/me ends that.
Switch account Sign out, then a fresh sign-in through the same way in. An OIDC issuer is asked with prompt=login; shoo.dev honours no such flag and answers with the Google account it remembers.
Add an account The old "Sign in" beside a session, named for what it does: another identity attached to this principal. Refused in plain words when the identity already belongs to someone else.

Signing in never opens a vault. Unlocking never signs you in. A sign-in that comes back to a device with a sealed vault lands on Unlock with the account named above the tabs — and a lock keeps the account unless Settings says otherwise.

Key the vault · this device · ends with Lock

Sealed vault — what was enrolled Passkey, PIN, password: any one opens it, and the unlock screen offers exactly those. A challenge the vault never enrolled fails like a wrong one, but is not a tab.
→
Authenticator code Step 2, only when enrolled, announced before step 1. The seed lives under the vault key, so the code can only ever follow a right key.
→
Open The key is in memory; the vault's sealed settings come with it. Idle, tab-hide and the lock buttons drop it.
→
Lock Drops the key and everything that left the vault (clipboard, staged claims). The account stays signed in — "Sign out of Identity too" is the strict preference.
Enrolling MFA Needs a primary method first — a guest has no key on disk for a code to guard, and a vault with a code but no key is one nothing can open. The gate is written only after a code from the app matches.
A vault that already has a code and no key Said out loud on Unlock: no tab can open it, delete it and seal again. Never three tabs that all fail.
