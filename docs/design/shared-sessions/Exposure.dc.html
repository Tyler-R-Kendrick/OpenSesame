What a shared session may carry

The line is already drawn in docs/security/key-hierarchy.md: a valid sign-in is not possession of the vault key. The session channel lives on the session-plane side of it and stays there. ADR 0079.

May cross the transport

  • the session id, and the roster this viewer is entitled to see
  • roles and grant metadata — subject, scope, expiry
  • presence and activity naming references: an item id, a collection id
  • ciphertext already sealed for one named recipient's key — the channel is a courier, not a party
  • signalling for the channel itself

Never crosses it, under any framing

  • the vault root key or any wrapper of it — passkey PRF output, the password KEK, the recovery key, the device KEK
  • a collection key or an item key in the clear
  • any access token, claim token or session bearer
  • a raw secret value, or a decrypted attachment
  • anything from the authority plane — receipt signing keys, sealed CA or signer keys, HSM PINs
  • item names and titles. "Tyler opened AWS root credentials" leaks the label to everyone, including a participant granted a different row

A shared session cannot be serverless

Every candidate transport needs one. WebRTC needs signalling and, in practice, a relay; SignalR and WebTransport are server protocols outright. Setup just established that signing in needs no service at all — sharing is the feature that reintroduces the dependency, so the share screen says so and offers the road to a Host.

A peer mesh would leak addresses

ICE candidates carry host and reflexive addresses, so every peer learns every other peer's IP. On a public session a stranger who has merely asked to join would learn the operator's home address. Hence: a Host-served channel, admission before any connection, and relay-only candidates if a peer path is ever added for large transfers.

Revocation is re-keying, not a switch

Withdrawing a grant stops new reads at once, but a participant who copied ciphertext keeps the key they were given for it. Future versions become unreadable only when the item is re-keyed. This is why every grant is time-bound by default and a standing one is a named exception.

Granularity the key hierarchy already has

Whole vault
wrap the collection key for the grantee
Chosen rows
wrap each item's own key for the grantee

Row level is not a filter over a collection read — that would be theatre. It is a direct grant in the policy model, additive to a collection grant and never able to widen one.

Expiry rides the feed we already trust

A grant is a thing with a deadline, so it joins the lifecycle scanner beside certificates and rotations rather than keeping a private timer — the rule ADR 0074 set. It inherits the whole ladder (notice, warning, urgent, expired) and delivers on the webhook endpoints that already exist, with retry.

And the payload is value-blind by construction: the event type has no field able to carry a value. An expiry notification structurally cannot carry what was granted, however carelessly a future subscriber is written.
